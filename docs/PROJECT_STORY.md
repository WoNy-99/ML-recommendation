## 1. 출발점: 2025 팀 프로젝트

- **목표**: Yelp 리뷰·카테고리로 사용자 취향을 표현해 음식점을 추천하고, OpenTable 데이터에서 전이 성능을 확인했습니다.
- **구성**:
  - 개인 담당 TF-IDF 콘텐츠 기반 추천
  - 팀원 담당 KNN·AutoEncoder
  - 세 점수를 가중 결합한 하이브리드
- **개인 담당(TF-IDF)**:
  - 음식점별 리뷰·이름·카테고리를 문서로 만들어 TF-IDF(10,000 features)로 벡터화했습니다.
  - 좋아한 음식점 벡터를 평균해 사용자 프로필을 만들고, 내적 점수로 Top-10을 추천했습니다.
- **당시 문제 해결**:
  - 30,000 features에서 메모리가 부족해 10,000으로 줄였습니다.
  - `numpy.matrix` 호환 오류를 고쳤습니다.
  - CSR 희소 연산, 사용자 샘플링, 후보 제한을 적용했습니다.
- **과거 보고 수치**:
  - TF-IDF Recall@10 0.0267(평가 375명)
  - 하이브리드 Recall@10 0.1189(평가 1,270명, 팀 결과)
  - TF-IDF OpenTable Category-Hit@10 ≈ 0.41
  - 평가 사용자 수와 조건이 서로 달라, 이 수치를 아래 2026 결과와 직접 비교하지 않습니다.

## 2. 다시 점검하며 발견한 문제 (관찰)

팀 프로젝트가 끝난 뒤 개인 담당 코드(`tfidf_main.py`, `preprocessing.py`)를 다시 읽으며 평가 구조를 점검했습니다.

| 발견 | 근거 위치 | 영향 |
|---|---|---|
| 데이터 분할 **전에** 전체 리뷰로 음식점 문서를 만들고 TF-IDF를 학습함 | `tfidf_main.py` 27–35행(문서·학습), 48–49행(분할) | 평가 정답 리뷰가 정답 음식점 문서·어휘·IDF에 포함됨 |
| 사용자 프로필도 같은 음식점 벡터를 평균함 | 같은 파일 55–64행 | 프로필 이력은 학습 구간이어도, 평균하는 벡터에 평가·미래 리뷰가 섞임 |
| "마지막 리뷰"가 날짜 기준이 아님 | `user_id` 정렬 후 `tail(1)`, 전처리에서 `date`·`review_id` 제외 | 시간 순서를 지킨 평가가 아님 |
| 평가 사용자 선택·프로필 표본에 seed가 없음 | 95행, 62행 | 다시 실행하면 결과가 달라질 수 있음 |
| 문서와 코드가 다름 | README "unigram·bigram" ↔ 코드 `ngram_range=(1,1)` | 설명 정정 필요 |

이 누수가 과거 수치를 얼마나 바꿨는지는 따로 측정하지 않았습니다(가설: 정답 점수를 부풀렸을 가능성). 그래서 과거 수치는 "과거 보고"로만 남기고, 새 평가 구조를 처음부터 다시 만들었습니다.

## 3. 평가 구조 다시 세우기 (B1)

- **데이터 범위**: Yelp 원본 zip을 풀지 않고 스트리밍으로 읽어 Pennsylvania 음식점만 추렸습니다.
  - zip 안의 `.tar`가 실제로는 gzip 압축이어서 첫 실행이 실패했습니다. 앞 바이트로 압축 형식을 판별하도록 고쳤습니다(관찰).
  - 결과: 음식점 12,641곳, 리뷰 1,100,250건, 2005-02 ~ 2022-01.
- **전역 시간 분할**:
  - 학습: 2021-01-01 이전
  - 검증: 2021-01-01 ~ 2021-06-30
  - 테스트: 2021-07-01 이후. 테스트 구간은 아직 평가하지 않았습니다.
  - 경계 시각과 같은 리뷰는 뒤 구간에 넣습니다.
  - 음식점 문서, TF-IDF 어휘·IDF, 사용자 프로필, 인기순 집계는 모두 학습 구간 리뷰만 씁니다.
- **정답 정의(visit)**: 평가 기간에 리뷰한 음식점 중 이전 이력에 없고 학습 후보에 있는 음식점 **집합**입니다. 바로 다음에 방문할 한 곳을 예측하는 평가가 아닙니다.
- **기준선**: 인기순·TF-IDF·무작위 세 모델을 같은 평가 사용자, 같은 후보, 같은 방문 제외 규칙으로 비교했습니다.
- **지표**:
  - Recall@10
  - nDCG@10: m = min(정답 수, 10), IDCG = Σ_{i=1..m} 1/log2(i+1)
  - 손으로 계산한 작은 예제로 검증했습니다.

## 4. 외부 AI를 어디에 쓸지: 검토한 후보와 선택

| 후보 | 내용 | 결과 |
|---|---|---|
| 리뷰 속성 분류 | 리뷰 텍스트를 외부 API로 보내 음식·서비스 평가를 분류 | 코드·합성 시험까지 작성. Yelp 데이터 이용 조건(데이터를 제3자에게 제공하지 않는다는 조항)을 검토한 뒤, **실제 리뷰 전송은 보류** |
| 로컬 소형 모델 | 같은 API 형식의 소형 모델을 PC에서 실행 | 설치·모델 다운로드가 필요해 시도하지 않음 |
| **사용자 질문 해석** | 사용자가 입력한 질문만 외부로 보내 음식 종류를 해석하고, 데이터와 추천 계산은 로컬에 유지 | **채택** |

채택 이유: 외부 AI의 역할을 "사용자 질문 해석"으로 좁히면 Yelp 리뷰·음식점 목록·추천 결과를 밖으로 보내지 않고도, 자연어 질문을 기존 TF-IDF 추천에 연결할 수 있습니다.

## 5. Jev / OpenJev를 고른 이유

"다른 LLM보다 정확해서" 고른 것이 아닙니다. 아래 세 층을 구분해 설명합니다.

### A. 공식 문서상 특징 (2026-10-22 조회, 읽기 전용)

- **System One 방식** (codiv.ai/docs):
  - 문서는 System One 모델이 문장을 생성하는 대신, 데이터에 대한 정해진 형식의 질문(yes/no인 `noul`, `choice`, `score`)에 선택지별 확률과 함께 답한다고 설명합니다.
  - 적합한 용도로 "문장보다 라벨과 확률이 필요한 분류·라우팅"을 듭니다. 문장 출력이 필요하면 생성형 모델을 권합니다.
- **Choice 반환 형식** (codiv.ai/docs, docs.typesafe.ai/primitives/choice):
  - 답마다 선택값(`choice`), 선택지별 확률(`probabilities`), 분포의 퍼짐으로 계산한 `confidence`가 옵니다.
  - 응답 전체에는 사용량(`usage.input_tokens`)이 붙습니다.
  - 구조화된 반환은 일반 LLM의 구조화 출력 기능으로도 얻을 수 있어서, OpenJev만의 장점으로 보지 않습니다.
- **답을 읽는 방식** (codiv.ai/docs/models, codiv.ai/docs/guides/read-options):
  - `openjev-0.1`은 DiffusionGemma 26B-A4B(이산 diffusion 언어모델)를 System One 모델로 쓰는 방식입니다. 답 칸을 정해 두고, 한 번의 denoising step에서 각 칸의 확률 분포를 읽습니다. 문장을 생성해 해석하지 않으므로 답이 정한 형식을 벗어나지 않는다고 설명합니다.
  - 기본은 1회 읽기입니다. 불확실한 답이 있으면 다른 노이즈로 3회 더 읽어 평균하며, 이 추가 읽기는 지연을 늘릴 수 있습니다.
  - 분류용으로 추가 학습했다는 설명은 문서에 없습니다.
- **제공자의 성능 주장과 우리 측정은 다릅니다**:
  - 문서는 질문 몇 개의 요청이 보통 "모델 시간 100ms 미만"이라고 말하고, 확률이 "보정되어 있다"고도 표현합니다. 이것은 **제공자의 주장**입니다.
  - 이 프로젝트가 잰 값은 네트워크를 포함한 클라이언트 측 요청 지연입니다(아래 C). 두 값은 다른 측정입니다.
  - confidence를 보정된 정답 확률로 해석하지 않습니다.
- **Jev와 OpenJev의 관계** (github.com/razorback16/openjev, codiv.ai/docs/guides/jev-compatibility):
  - Jev는 TypeSafe의 모델입니다.
  - OpenJev는 같은 요청·응답 형식을 따르는 독립 오픈소스 서버이고, TypeSafe와 제휴 관계가 아니라고 밝힙니다.
  - 이 프로젝트는 Codiv가 호스팅하는 OpenJev(`openjev-latest`)만 호출했습니다. TypeSafe Jev는 호출하지 않았습니다.

### B. 이 프로젝트에 맞았던 이유

- **필요한 일**: 자유로운 추천 문장을 만드는 것이 아니라, 질문이 원하는 음식 종류를 **고정된 선택지**(이탈리안·일식·멕시칸·기타·언급 없음·모호함)로 해석하는 것이었습니다.
- **연결 방식**: 반환된 라벨을 로컬 카테고리 필터에 1:1로 연결할 수 있었습니다. 모호하거나 지원하지 않는 라벨은 추천하지 않는 상태로 보낼 수 있었습니다.
- **기존 구조 유지**: 기존 로컬 TF-IDF는 그대로 두고, 외부 AI의 역할만 질문 해석으로 좁게 추가했습니다. Yelp 데이터·후보·추천 결과는 외부로 보내지 않습니다.
- **도입에 든 일 / 학습 필요 여부 / 운영 비용**:
  - 도입 작업: 질문·선택지 정의(YAML) 작성, 요청·응답 검사, 재시도·예산 기록 코드, 로컬 조건 연결
  - 별도 학습: 이번 적용에서는 모델을 학습하거나 미세조정하지 않았습니다. 질문 정의와 API 호출만으로 연결했습니다.
  - 운영 비용: 질문 3개 입력 658토큰. 공개 문서상 무료 등급이며, 실제 청구 여부는 확인하지 않았습니다.
  - 다른 방식(직접 분류기 학습, 일반 LLM 등)과 개발 비용·성능을 비교하지는 않았습니다.

### C. 실제로 확보한 효과 (관찰, 직접 작성한 질문 3개)

- 세 질문 모두 사전에 기록한 기대 라벨과 같은 라벨이 나왔습니다(italian, japanese, ambiguous). 한국어 질문 2개, 영어 질문 1개입니다.
- 라벨이 실제 로컬 후보 필터에 반영됐습니다(Philadelphia + 해당 카테고리 → 후보 496곳, 285곳).
- 모호한 질문은 임의로 추천하지 않고 재확인 상태로 처리했습니다.
- 응답 모델은 `openjev-0.1`이었고, 재시도 없이 3번 요청했으며, 입력은 합계 658토큰이었습니다.
- 네트워크를 포함한 요청별 지연은 1,313 / 1,500 / 797ms였습니다. 이 값은 모델 추론 시간도, 전체 추천 처리 시간(로컬 데이터 적재·TF-IDF 포함)도 아닙니다.
- **확대하지 않는 것**:
  - 질문 3개는 연결 확인입니다. 분류 정확도가 100%라거나 다른 모델보다 빠르다·저렴하다·정확하다고 말하지 않습니다.
  - 추천 품질이 향상됐다거나 비용이 절감됐다고도 말하지 않습니다.

## 7. 실행 결과

### B1 검증 기준선 (관찰)

- **조건**: 검증 구간, visit, 같은 평가 사용자 5,000명(조건 충족 7,836명 중 seed 42로 추출)
- **실행**: 실행 ID `20261022-012737_validation`, `20261022-012949_validation`의 `results.json`

| 모델 | Recall@10 | nDCG@10 |
|---|---:|---:|
| 인기순 | 0.0147761 | 0.0081812 |
| TF-IDF | 0.0083577 | 0.0048970 |
| 무작위 | 0.0006725 | 0.0003102 |

- **재현 확인**: 두 실행에서 다음이 모두 같았습니다.
  - 지표
  - 평가 사용자 목록 해시
  - 설정·코드·데이터 해시
- 달라진 것은 실행 메타데이터였습니다: 실행 시각(실행 폴더 이름), 실행 시간, MLflow run ID 등. 지표와 식별 정보에는 차이가 없었습니다.
- **한계**: 차이에 대한 통계 검정은 하지 않았고, 테스트 구간은 평가하지 않았습니다.

#### 인기순 > TF-IDF 결과 해석: 두 관찰 분석으로 원인 후보를 좁혔고, 인과는 확정하지 않음

개인화 모델인 TF-IDF가 인기순보다 낮게 나온 것은 예상과 다른 결과였습니다. 이 결과를 그대로 적거나 모델을 바로 바꾸기보다, 먼저 왜 이런 결과가 나왔는지 해석할 수 있는 관찰 분석 두 가지를 정해 두고 저장된 결과로 실행했습니다.

**코드에서 확인한 구조 (사실)**
- 인기순은 학습 기간에 그 음식점을 리뷰한 고유 사용자 수로 순위를 매깁니다.
- TF-IDF 프로필은 사용자가 별점 4 이상을 준 음식점들의 벡터를 같은 비중으로 평균합니다.
- 정답(visit)에는 별점 제한이 없습니다. 평가 기간에 처음 리뷰한 음식점이면 낮은 별점이어도 정답입니다.

**분석 전에 세운 원인 후보 (가설)**
- 평가 기간에 새로 방문한 음식점이 원래 인기 있는 곳에 몰려 있다면, 인기순에 유리할 수 있습니다.
- 개인화에 쓸 긍정 이력이 짧은 사용자는 프로필이 빈약해서 TF-IDF가 불리할 수 있습니다.
- 오래된 이력까지 같은 비중으로 평균하면서 최근 취향이 묻힐 수 있습니다. 이 가설은 이번 분석 범위 밖의 후속 후보입니다.

**분석 방법** (`src/analyze_baseline.py`)
- 모델을 다시 학습하거나 추천을 다시 실행하지 않습니다. 저장된 평가 사용자 목록, 사용자별 지표, 준비된 리뷰의 날짜·별점·ID 필드만 씁니다.
- **A. 정답의 인기도 분포**
  - B1과 같은 학습 구간, 후보, 인기도, 동률 규칙으로 후보를 인기 순서대로 세웁니다.
  - 상위 10%·20%(사전에 고정, 올림 처리)에 속한 음식점이 평가 정답에서 차지하는 비중을 구합니다.
  - 비중은 두 가지 기준으로 냅니다. 하나는 전체 사용자-정답 쌍 기준이고, 다른 하나는 사용자별 비중의 평균입니다. 뒤의 것은 사용자별 평균 Recall과 같은 단위로 맞춘 값입니다.
- **B. 긍정 이력 길이별 성능**
  - 학습 구간에서 별점 4 이상을 준 서로 다른 음식점 수로 사용자를 1곳 / 2~4곳 / 5곳 이상(사전 고정) 구간으로 나눕니다.
  - 구간마다 사용자 수, 두 모델의 Recall@10·nDCG@10 평균, TF-IDF − 인기순 차이를 구합니다.
  - 전체 평균은 원래 결과 파일과 대조합니다.
- 두 분석 모두 관찰 집계입니다. 인기도가 집중돼 있거나 구간별로 차이가 난다고 해서, 그것이 인기순 우위의 원인임을 입증하지는 않습니다.
- 실행 전에 설정 사본·평가 사용자 목록·데이터 해시를 원래 실행 기록과 대조하고, 하나라도 다르면 멈추게 했습니다.

**분석 결과 (관찰)**
- 실행: 소스 `20261022-012737_validation`, 산출물 `artifacts/analysis/20261022-041618_baseline-analysis/analysis.json`
- 사용자별 지표의 전체 평균이 원래 결과 파일과 전체 자릿수까지 같았습니다. 평가 사용자 5,000명이 세 구간에 빠짐없이 나뉘었습니다.

*A. 정답의 인기도 분포* — 후보 12,351곳, 사용자-정답 쌍 10,340개

| 인기 상위 집합 | 음식점 수 | 집합 안 정답 쌍 | 쌍 기준 비중 | 사용자별 비중 평균 |
|---|---:|---:|---:|---:|
| 상위 10% | 1,236곳 | 3,724 | 36.02% | 32.37% |
| 상위 20% | 2,471곳 | 5,463 | 52.83% | 49.55% |

- 학습 기간 인기 상위 10%의 음식점에 평가 정답 쌍의 약 36%가 들어 있었습니다. 정답이 학습 기간 인기 음식점에 집중돼 있다는 관찰입니다.
- 참고로, 정답이 후보 전체에 고르게 퍼져 있다고 가정하면 비중은 집합 크기 비율(약 10%·20%)에 가까울 것입니다. 이것은 가정적 참고 기준이며, 무작위 모델의 실제 성능이나 개선율이 아닙니다.
- 정답 수로 가중한 비중(쌍 기준)이 사용자별 단순 평균보다 높았습니다. 정답 수와 인기 음식점 비중의 구체적인 관계는 따로 분석하지 않았습니다.
- 상위 10% 집합은 1,236곳이고 추천은 10곳이므로, 이 집중이 Top-10 추천에서 인기순이 앞선 원인을 직접 입증하지는 않습니다.

*B. 긍정 이력 길이별 성능* — 서로 다른 사용자 집단의 평균 비교

| 긍정 이력 | 사용자 수 | Recall 인기순 | Recall TF-IDF | Recall 격차(인기순 − TF-IDF) | nDCG 인기순 | nDCG TF-IDF |
|---|---:|---:|---:|---:|---:|---:|
| 1곳 | 1,325 | 0.0178994 | 0.0122516 | 0.0056478 | 0.0092068 | 0.0072042 |
| 2~4곳 | 1,558 | 0.0133743 | 0.0096063 | 0.0037680 | 0.0081969 | 0.0054487 |
| 5곳 이상 | 2,117 | 0.0138529 | 0.0050016 | 0.0088513 | 0.0075277 | 0.0030468 |

- 세 구간 모두 인기순이 높았습니다. Recall 격차는 1곳 → 2~4곳에서 줄었다가 5곳 이상에서 가장 컸습니다. 이력 길이에 따라 한 방향으로 커지거나 줄지는 않았습니다.
- 짧은 이력 구간에서 격차가 가장 크지는 않았습니다. 따라서 긍정 이력 부족만으로 전체 결과를 설명하기는 어렵습니다. 구간별 사용자 구성의 영향은 확인하지 않았습니다.
- 서로 다른 사용자 집단을 비교한 결과이므로, 한 사용자의 이력이 늘어나면 성능이 떨어진다는 뜻이 아닙니다.

**해석과 남은 질문**
- 인기순이 TF-IDF보다 높은 결과를 확인했고, 이를 해석하려고 정답의 인기도 분포와 긍정 이력 길이별 성능을 분석했습니다.
- 정답의 인기도 집중을 관찰했고, 이력 부족만으로는 설명하기 어려운 구간별 패턴도 확인했습니다. 그래서 "이력이 짧아서 TF-IDF가 불리하다"는 처음 가설만으로는 부족하다고 다시 보고, 아래 후보를 다음에 확인할 질문으로 남겼습니다.
- 원인 후보는 좁혔지만 인과관계는 확정하지 않았습니다.
- 미검증 후속 후보:
  - 긴 이력을 같은 비중으로 평균할 때 프로필이 희석되는지
  - 구간별 정답 수·인기 정답 비중의 차이
  - 이미 방문한 음식점을 후보에서 빼는 처리의 영향
- 통계 검정·신뢰구간·테스트 구간 평가는 하지 않았습니다. 이 분석은 OpenJev 질문 해석 경로와 별개이며, OpenJev가 추천 품질을 높였다는 근거가 아닙니다.

## 8. 재현성 기록 방식

- **기준선 실행**: 실행마다 새 폴더를 만들어 다음을 남깁니다.
  - 설정 사본과 해시
  - 평가 사용자 목록과 해시
  - 데이터 파일 해시
  - Git 커밋과 미커밋 여부
  - `src` 코드 파일별 해시
  - 패키지 버전
  - 로그와 지표
  - 로컬 MLflow(sqlite)에도 같은 지표와 식별 정보를 남깁니다.
- **질문 해석 실행**:
  - 시작할 때 실행 설정·질문 정의·baseline 설정을 바이트 그대로 사본으로 남깁니다.
  - 로컬 추천은 그 사본으로 실행합니다.
  - 외부 호출에는 누적 예산 기록(요청 수·추정 입력량)이 있어, 정한 횟수를 넘겨 호출하지 않습니다.
- **비밀 정보**: API 키는 환경변수로만 받고, 로그·결과·사본에 남기지 않습니다. API 주소·경로는 설정 파일로 분리했습니다. 이것은 주소를 숨기는 조치가 아니라 설정을 분리한 것입니다.
- **시험**: 합성 자료와 가짜 네트워크로 만든 시험 136개(관찰 분석 시험 10개 포함)가 로컬 환경(Windows, Python 3.11)에서 모두 통과했습니다(사용자 실행 보고). 다루는 범위는 다음과 같습니다.
  - 분할 경계, 누수, 지표 계산
  - 재시도·중단·예산
  - 전송 필드, 설정 사본

## 9. 한계와 남은 과제

- **B1**: 두 관찰 분석으로 인기순 우위의 원인 후보를 좁혔지만 인과는 확정하지 않았습니다(§7). 프로필 희석·구간 구성·방문 제외의 영향은 미검증이고, 통계 검정과 테스트 구간 평가도 남아 있습니다.
- **질문 해석**:
  - 질문 3개로 연결만 확인했습니다. 직접 작성한 질문 세트와 사람 정답으로 키워드 방식과 OpenJev를 비교하는 평가는 후속 후보입니다.
  - 지역은 등록된 별칭만 인식합니다.
  - 음식 종류는 세 가지만 다룹니다.
- **리뷰 속성 분류**: 코드와 합성 시험까지만 진행했습니다. 실제 리뷰 적용은 데이터 이용 조건 때문에 보류 중입니다.
- **추천 품질**: 질문 기반 추천 목록의 품질은 평가하지 않았습니다.

## 10. 개발 방식

- AI 코딩 도구(Claude Code)가 코드·시험·문서를 작성했습니다.
- 다른 AI 도구(Codex)가 매 단계 읽기 전용으로 검수했습니다.
- 프로그램·시험 실행, 데이터 범위, 분할 경계, 정답 정의, 외부 호출 승인 같은 결정은 직접 내렸습니다.
- 작업 지시 → 구현 → 검수 지적 → 수정 → 실행·결정 순서로 반복했습니다.
- 예를 들어 다음 문제는 검수와 실제 실행 단계에서 드러나 수정했습니다.
  - nDCG 정의
  - macro-F1 계산 방식
  - 재시도 대기 시간
  - 압축 tar 처리
- 프로그램 안에 스스로 실험하는 에이전트를 구현한 것은 아닙니다.
